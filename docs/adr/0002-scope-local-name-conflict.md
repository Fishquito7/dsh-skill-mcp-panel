# 同名冲突只在目标作用域内判定

「添加技能」此前用 `winnerEntry(allEntries, name)` 当门禁：只要这台机器上**任何地方**（用户根、任意工作区根）存在同名技能就拒绝落盘。于是往工作区 A 添加一个工作区 B 早已有的名字会被拒，往全局添加一个某工作区已有的名字也会被拒——而 DSH 的发现根按**会话 cwd** 解析，A 的会话根本看不到 B 的 `.dsh/skills`；全局与工作区同名也只是注册表按根优先级裁决（project 100 < user 400，近层遮蔽远层，被遮蔽项没有 API 可枚举）。插件自己的行级操作（查看 / 启停 / 删除 / 迁移）从 0.6.4 起就按（名称 + 作用域）精确定位，只有添加这一条还把跨作用域同名当致命错误，行为不自洽。

现在：冲突判定收窄到**目标作用域**（全局，或该工作区的项目根——同工作区的 `.dsh/skills` 与 `.agents/skills` 属同一作用域）；目标作用域内已有同名仍是硬跳过，跨作用域同名照常落盘并随结果返回一条 `warnings` 提示（面板与 `dsh-panel skill add` 都打印）。同一批选择内部的同名（`batchNames`）仍然跳过：那两条会撞同一个落盘路径。

## Considered Options

- **保持全机器唯一**：实现最简单，但把 DSH 允许、且面板其它操作都支持的状态当成错误，用户没法把同一个技能放进第二个工作区。
- **完全不管重名**（连同作用域也放行）：同作用域会出现两个互相遮蔽的同名实体，按名字定位的行级操作产生歧义。
- **只保留 `pathExists(target)` 那一道**：漏掉同作用域但不同路径的情形（目录束 `<根>/<名>/` 与单文件 `<根>/<名>.md`），二者同名却都不触发路径冲突。

## Consequences

- `AddResult` 新增 `warnings` 字段（Typert schema 同步）；面板消息里提示排在跳过之前。
- `skipped` 的语义收窄为"这条没能落盘"，不再表示"这台机器上别处有同名"。
- 全局与工作区可以同名共存，谁生效由 DSH 的根优先级决定，插件不替它裁决。
